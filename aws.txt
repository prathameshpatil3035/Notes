# AWS Notes and Cloud Platform Comparison

## Traditional vs Cloud Platform to Host Website

- **Traditional Methods (On-Premises Hosting):**
  - **Server Cost:** High initial capital expense for hardware; ongoing maintenance costs.
  - **Scale Up/Down:** Scaling requires manual purchase and installation of hardware; slow and expensive.
  - **Examples:** Own data centers, dedicated hosting providers.
  
- **New Cloud Platforms:**
  - **Server Cost:** Pay-as-you-go, operational expenses reduce upfront costs.
  - **Scale Up/Down:** Instant, automated scaling; resources adjust dynamically based on demand.
  - **Examples:** Amazon Web Services (AWS), Microsoft Azure, Google Cloud Platform (GCP), IBM Cloud, Oracle Cloud.

## What is AWS?

Amazon Web Services (AWS) is a comprehensive cloud computing platform provided by Amazon that offers a vast range of on-demand services including computing power, storage, and databases, enabling businesses to deploy applications globally with high reliability and scalability.

## Use of AWS

- Host websites and applications
- Data storage and backup
- Big data processing and analytics
- Machine learning model deployment
- Content delivery networks (CDN)
- Disaster recovery solutions

## Features or Advantages of AWS

- Wide global infrastructure with multiple data centers
- Pay-as-you-go pricing model
- High scalability and flexibility
- Robust security and compliance certifications
- Vast ecosystem of services and third-party integrations
- Reliable performance with Service Level Agreements (SLAs)

## 3 Types of AWS Services

| Service Type                           | Description                                                                                                | AWS Examples                                      |
|----------------------------------------|------------------------------------------------------------------------------------------------------------|---------------------------------------------------|
| **IaaS (Infrastructure as a Service)** | Provides virtualized computing resources over the internet. Users manage OS, middleware, apps.             | Amazon EC2 (virtual servers), Amazon S3 (storage) |
| **PaaS (Platform as a Service)**       | Provides platform allowing customers to develop, run, manage applications without managing infrastructure. | AWS Elastic Beanstalk, AWS Lambda                 |
| **SaaS (Software as a Service)**       | Software hosted in the cloud available to users over the internet.                                         | Amazon Chime (communications), AWS WorkDocs       |

## Types of Cloud Deployment Models

- **Public Cloud:** Services delivered over the internet and shared across organizations (e.g., AWS, Azure, GCP)
- **Private Cloud:** Exclusive cloud environment for a single organization, often on-premises or hosted privately.
- **Hybrid Cloud:** Combination of public and private clouds allowing data and applications to be shared between them.

# AWS Regions, Availability Zones, Data Centers, and Local Zones
================================================================

## AWS Regions
- AWS Regions are separate geographic areas around the world where AWS deploys data centers.
- Each region is independent and consists of multiple Availability Zones.
- Example region codes: `us-east-1` (N. Virginia), `eu-central-1` (Frankfurt), `ap-south-1` (Mumbai).

## Availability Zones (AZs)
- Availability Zones are isolated, physically separate data centers within a region.
- Each AZ has independent infrastructure including power, networking, and cooling.
- AZs are connected by high-speed, low-latency links and offer fault isolation to applications.
- AZ naming: region code plus a letter, e.g., `us-east-1a`, `us-west-2b`.
- Use multiple AZs to ensure high availability for applications.

## Data Centers
- Data centers are the actual physical buildings housing AWS servers and networking hardware.
- Multiple data centers make up an Availability Zone.
- Designed with redundant power, security, and network connectivity to ensure continuous operation.

## Local Zones
- Local Zones bring AWS infrastructure closer to large population centers for ultra-low latency access.
- They extend a parent AWS Region to the location of end-users.
- Local Zone codes include region plus location plus an identifier, e.g., `us-west-2-lax-1` (Los Angeles Local Zone).
- Useful for applications requiring very low latency (media processing, gaming, financial services).

----------------------------------------------------
How IAM permission evaluation works (important rule)
----------------------------------------------------

AWS IAM follows this order:
Explicit DENY
Explicit ALLOW
Default DENY (if nothing matches)

🚨 Explicit DENY always wins, no matter where it comes from.

Group A
Explicitly DENIES S3 read and write

Group B
Explicitly ALLOWS S3 read and write

IAM User
Added to both Group A and Group B

If an IAM user belongs to both an Allow and a Deny group for S3, the Deny always wins and the user cannot read or write.

AWS IAM (Identity and Access Management)
==========================================================================

IAM is a GLOBAL AWS service (not region-specific)
Used to control WHO can access AWS and WHAT they can do

--------------------------------------------------------------------------

1) IAM – What & Why
-------------------
What:
IAM allows you to manage identities (users, roles) and permissions (policies)
to securely control access to AWS services and resources.

Why:
- Avoid using root user for daily work
- Apply least privilege access
- Secure AWS accounts
- Enable audit, compliance, and cost control

Key Concepts:
- Authentication: Who you are (login)
- Authorization: What you can do (permissions)

--------------------------------------------------------------------------

2) IAM Users
------------
What:
An IAM User represents a human or application that needs access to AWS.

Why:
- Individual access tracking
- Separate credentials
- Easy permission management

Types of Access:
- Console access (username + password)
- Programmatic access (Access Key + Secret Key)

Steps to Create:
AWS Console → IAM → Users → Create user
- Enter username
- Select access type
- Attach permissions (policy or group)
- Enable MFA (recommended)

Best Practice:
- One user = one person
- Do not share users
- No permissions directly if possible (use groups)

--------------------------------------------------------------------------

3) IAM User Groups
------------------
What:
A collection of IAM users with shared permissions.

Why:
- Easier permission management
- Centralized access control
- Scales well

How it Works:
Permissions are attached to groups
Users inherit permissions from groups

Steps to Create:
IAM → User groups → Create group
- Name group
- Attach policies
- Add users

Best Practice:
- No direct permissions to users
- Use role-based groups (Admin, Developer, ReadOnly)

--------------------------------------------------------------------------

4) IAM Policies
---------------
What:
A JSON document that defines permissions.

Why:
- Fine-grained access control
- Secure resource usage

Policy Types:
- AWS Managed (created by AWS)
- Customer Managed (created by you)
- Inline Policy (attached to one user/group/role)

Policy Structure:
- Effect: Allow / Deny
- Action: What operation
- Resource: On which resource
- Condition: Optional rules

Important Rule:
Explicit DENY always overrides ALLOW

Steps to Create Customer Managed Policy:
IAM → Policies → Create policy → JSON/Visual editor → Review → Create

Best Practice:
- Use least privilege
- Prefer customer managed policies for control

--------------------------------------------------------------------------

5) Account Settings – Password Policy
-------------------------------------
What:
Defines rules for IAM user passwords.

Why:
- Improve security
- Prevent weak passwords

Configurable Rules:
- Minimum password length
- Require uppercase, lowercase, numbers, symbols
- Password expiry
- Password reuse prevention

Steps:
IAM → Account settings → Password policy → Edit

Best Practice:
- Enforce strong password policy
- Enable password rotation

--------------------------------------------------------------------------

6) MFA (Multi-Factor Authentication)
------------------------------------
What:
Adds an extra authentication layer (something you have).

Why:
- Protect against credential compromise
- Mandatory for root user

Types:
- Virtual MFA (Google Authenticator, Authy)
- Hardware MFA
- U2F Security Key

Where Used:
- Root user
- IAM users
- IAM roles (via session policies)

Steps:
IAM → Users → Security credentials → Assign MFA device

Best Practice:
- Enable MFA for root user (mandatory)
- Enable MFA for privileged IAM users

--------------------------------------------------------------------------

7) Security Credentials (User)
------------------------------
Includes:
- Password (console)
- Access keys (CLI / SDK)
- MFA devices
- SSH keys (CodeCommit)

Why:
Used to authenticate IAM users.

Important:
- Access keys are sensitive
- Never commit to Git
- Rotate regularly

Steps to Create Access Key:
IAM → Users → Security credentials → Create access key

--------------------------------------------------------------------------

8) AWS CLI & Access Keys
------------------------
What:
AWS CLI allows command-line interaction with AWS services.

Why:
- Automation
- Scripting
- DevOps workflows

Requires:
- Access Key ID
- Secret Access Key

Steps:
1) Install AWS CLI
2) Run: aws configure
3) Enter access key, secret key, region

- Never use root access key

--------------------------------------------------------------------------

9) IAM Roles
------------
What:
An IAM identity with permissions but no long-term credentials.

Why:
- Secure service-to-service access
- No access key management
- Temporary credentials

Common Use Cases:
- EC2 accessing S3
- Lambda accessing DynamoDB
- Cross-account access

Role Components:
- Trust policy (who can assume role)
- Permission policy (what role can do)

Steps to Create:
IAM → Roles → Create role
- Select trusted entity
- Attach permissions
- Assign role to service

Best Practice:
- Always use roles for AWS services
- Avoid access keys in EC2/Lambda

--------------------------------------------------------------------------

10) AWS CloudShell
------------------
What:
Browser-based shell with AWS CLI preconfigured.

Why:
- No local setup required

Access:

Features:

Limitations:

--------------------------------------------------------------------------

11) Access Advisor (User & Group)
---------------------------------
What:
Shows which AWS services were actually used.

Why:

Available For:

--------------------------------------------------------------------------

12) Credential Report
---------------------

Account-wide report of all IAM users’ credentials.

- Security audit

--------------------------------------------------------------------------

13) Root User vs IAM User (Important)
------------------------------------
Root User:
- Full access to everything
- Cannot be restricted
- Used only for account setup

IAM User:
- Limited permissions
- Auditable
- Daily operations

Best Practice:
- Lock root user
- Enable MFA
- Never use root for daily work

--------------------------------------------------------------------------

IAM Best Practices Summary
--------------------------
- Enable MFA for root and admins
- Use groups instead of direct user permissions
- Use IAM roles for services
- Rotate access keys
- Apply least privilege
- Monitor via Access Advisor & Credential Report
- Enforce password policy

================================
AWS S3 (Simple Storage Service) 
================================

S3 is a GLOBAL service
Data is stored at REGION level
Highly durable, scalable, and cost-effective object storage

------------------------------------------------------------------

1) What is S3
-------------
What:
S3 is an object storage service used to store files like
images, videos, backups, logs, documents, static websites, etc.

Why:
- Unlimited storage
- 99.999999999% durability (11 nines)
- Highly available
- Secure and cost efficient

Basic Terms:
- Bucket → container for objects
- Object → file (data + metadata)
- Key → unique name of object

------------------------------------------------------------------

2) Bucket Basics
----------------
- Bucket name must be globally unique across AWS
- Bucket is created in ONE region
- Objects stay in that region unless replicated

Bucket Naming:
- lowercase only
- no spaces
- unique globally (not account-wise)

Example:
my-company-images-prod

------------------------------------------------------------------

3) Object & Folder Concept (Important)
--------------------------------------
S3 does NOT have real folders.

Folders are just part of object name (key).

Example object name:
images/2025/jan/photo.png

Reality:
- Single object
- No actual folder structure

AWS console only SHOWS folders for convenience.

Why this matters:
- Permissions
- Lifecycle rules
- Performance

------------------------------------------------------------------

4) Object Uniqueness
--------------------
Each object is uniquely identified by:
bucket-name + object-key

Example:
bucket: my-bucket
key: images/a.png

You can upload another image with SAME NAME:
- It overwrites existing object (if versioning disabled)
- Creates new version (if versioning enabled)

Bucket names are globally unique
Object names are unique only within bucket

------------------------------------------------------------------

5) S3 Versioning
----------------
What:
Keeps multiple versions of the same object.

States:
- Enabled
- Suspended (NOT disabled permanently)

Once enabled:
- Cannot be fully disabled
- Only suspended

Why:
- Protect from accidental delete
- Protect from overwrite
- Data recovery

Delete behavior:
If versioning ENABLED:
- Delete creates a DELETE MARKER
- Object appears deleted
- Older versions still exist

Permanent delete:
- Must delete specific version ID
- Only possible manually or via lifecycle

Recycle bin analogy:
Delete marker = recycle bin
Version delete = permanent delete

------------------------------------------------------------------

6) S3 Region Scope
------------------
- Buckets are region-specific
- Objects stay in bucket’s region
- Bucket name uniqueness is GLOBAL

Example:
Bucket in Mumbai
Object stored in Mumbai only

Replication needed for other regions
